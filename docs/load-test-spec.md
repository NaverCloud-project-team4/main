# 제보 자동 생성기 및 NCP 부하 테스트 명세서

- 작성일: 2026-10-27
- 상태: 초기 설계 명세. 구현과 실행 방법은 [실행 가이드](load-test.md)를 참고한다. 사진은 사용자 제공 6장으로 구성했고 고정 좌표 파일 대신 서버의 활성 서울 경계 안에서 무작위 좌표를 생성한다. 아래 예정 인터페이스와 달라진 실제 옵션은 실행 가이드를 기준으로 한다.
- 기준 코드: `main`, `fffa481`
- 목적: 실제 HTTP API로 사진 제보를 생성하고 피드 조회 부하를 발생시켜 처리량, 지연, 검증 대기, NCP 자동 확장의 동작을 확인한다.

## 1. 테스트 범위

테스트 클라이언트는 API 서버와 별도 장비에서 실행하고, 실제 사용자가 접근하는 Load Balancer의 API 주소를 사용한다. 특정 서버 IP에 직접 요청하면 분산과 신규 서버 편입을 검증할 수 없다.

| 모드 | 동작 | 확인 대상 |
|---|---|---|
| `submit` | 사진과 설명을 만들어 `POST /api/reports` 호출 | 이미지 처리, DB 저장, Object Storage 업로드, 제보 접수 |
| `feed` | `GET /api/reports`의 최신순·인기순·구별 페이지 조회 | 피드 API 및 DB 읽기 처리량 |
| `mixed` | 제보 생성과 피드 조회를 독립적인 속도로 동시에 실행 | 읽기·쓰기 동시 부하, 자동 확장 |

별도 관측 작업으로 제보 상태 및 승인된 제보의 피드 노출을 확인한다. 선택적으로 피드의 `photo_url`을 내려받아 이미지 전달 경로도 측정한다. 피드 JSON 조회만으로 사진 다운로드 부하를 재현했다고 판단하지 않는다.

기존 `app.cli seed-showcase`는 DB에 승인 데이터를 직접 만들고 AI 검증을 생략하는 시연 도구다. 부하 생성기는 실제 제보 API를 호출하며 이 시연 도구를 재사용하지 않는다. 필요하면 피드 읽기 테스트의 사전 데이터 준비에만 별도로 활용한다.

## 2. 현재 서버 계약과 제약

구현 시 `backend/app/main.py`, `config.py`, `schemas.py`, `storage.py`, `verifier.py`를 기준으로 한다. `docs/api.md`의 과거 설명과 다르면 현재 코드를 우선한다.

| 항목 | 현재 동작 | 생성기 처리 |
|---|---|---|
| 인증 | 로그인 후 Bearer JWT, 기본 만료 120분 | 측정 시작 전 로그인, 만료 전 갱신 로그인은 별도 계측 |
| 제보 간격 | 계정당 기본 5초, 환경설정으로 변경 가능 | 실제 배포값을 입력받아 계정별 발송 간격 준수 |
| 파일·수동 위치 | `photo_source=upload`, `location_source=manual`은 운영자만 허용 | 테스트 전용 운영자 계정 풀 사용 |
| 사진 | JPEG/PNG/WEBP, 기본 10 MiB 이하 | 업로드 전 실제 형식·바이트 수 검사 |
| 이미지 크기 | 최소 변 길이 32px, 종횡비 5:1 이내, Pillow 픽셀 제한 적용 | 디코딩 사전 검사, 과도한 해상도 제외 |
| 서버 이미지 처리 | EXIF 제거, RGB 변환, 최대 1600×1600 JPEG로 정규화 | 원본 업로드량과 저장된 사진 크기는 별도 항목 |
| 위치 | 활성 서울 자치구의 실제 경계 내부여야 함 | 사전 검증된 좌표 목록에서 선택 |
| 시즌 | 현재 활성 시즌 필요 | 1건 사전 제출로 유효성 확인 |
| 성공 응답 | HTTP 202와 제보 객체 | 접수 성공으로 기록. 공개 성공과 구분 |
| 운영 AI | production은 CLOVA 모드 필요, `demo_outcome` 불가 | 실제 검증 경로 유지, 강제 승인 필드 전송 금지 |
| 공개 조건 | `APPROVED`만 공개 피드에 노출 | 승인·검토·반려·대기를 구분해 집계 |

운영자 파일 업로드는 현재 서버가 제공하는 정상 경로다. 일반 사용자의 카메라·GPS UI 성능이나 권한 UX까지 검증하는 테스트는 이번 범위에 포함하지 않는다. 계정 역할은 사전 준비하고, 생성기가 권한 검사나 제보 간격 제한을 우회하지 않는다.

## 3. 실행 전에 필요한 입력

| 입력 | 필수 여부 | 내용 |
|---|---|---|
| API 기본 주소 | 필수 | 예: `https://api.example.com`. 측정 대상 LB 경유 주소 |
| 계정 파일 | 쓰기 테스트 필수 | 테스트 전용 운영자 계정의 이메일·비밀번호. 파일 경로로 전달하고 Git·결과물에서 제외 |
| 사진 목록 | 쓰기 테스트 필수 | 저장소 샘플 또는 사용자가 준비한 사진과 수종·단계 매핑 |
| 좌표 목록 | 쓰기 테스트 필수 | 위도·경도·기대 자치구. 실제 서버의 resolve API로 사전 확인 |
| 부하 단계 | 필수 | 단계별 시간, 초당 제보 수, 초당 피드 조회 수 |
| 실행 한도 | 필수 | 최대 제보 수, 동시 요청 수, 총 실행 시간, 업로드 바이트 수 |
| 제보 간격 | 쓰기 테스트 필수 | 배포 서버의 `REPORT_COOLDOWN_SECONDS` 실제 값. 기본값 5초를 조용히 확정하지 않음 |
| NCP 확장 설정 | 자동 확장 평가 필수 | 실제 감시 지표·임계값·평가 시간·최소/최대 서버 수·쿨다운 |
| 관측 자료 | 자동 확장 평가 필수 | 콘솔 실행 이력 또는 내보낸 지표, LB 대상 서버 상태 |

NCP 관리용 접근 키는 API 부하 생성 자체에는 필요하지 않다. 1차 구현에서는 NCP 지표와 실행 이력을 수동으로 수집해 결과 시간축과 대조한다. CLOVA와 Object Storage 키는 기존 서버 설정을 사용하며 클라이언트에 복사하지 않는다.

### 사진 준비

- 단순 접수 테스트는 저장소의 `assets/sample-maple.png`, `assets/sample-ginkgo.png`로 시작할 수 있다. 신규 사진 제출은 필수가 아니다.
- 실제 AI 검증과 피드 공개까지 보려면 단풍·은행이 선명한 실제 사진 10~30장 정도와 각 사진의 `stage`, `species`를 준비한다. 사진만으로 승인이 보장되지는 않는다.
- 같은 사진을 반복 사용해도 현재 제보 API는 사진 해시만으로 등록을 차단하지 않는다. 단, 반복 사진의 결과가 실제 이용자의 사진 다양성을 대표하지는 않는다.
- 업로드 부하를 비교하려면 작은 이미지와 큰 이미지를 각각 별도 시나리오로 실행한다. 파일 크기뿐 아니라 해상도·형식도 결과에 남긴다.
- 사진 목록은 측정 전에 메모리 또는 제한된 캐시에 준비한다. 파일 준비 시간과 생성기 자체 CPU 사용이 목표 부하를 제한하지 않게 한다.

사진 매니페스트 예:

```json
[
  {"path": "assets/sample-maple.png", "species": "MAPLE", "stage": "PEAK"},
  {"path": "assets/sample-ginkgo.png", "species": "GINKGO", "stage": "PEAK"}
]
```

위 수종·단계 값은 입력 예시다. 실제 AI 테스트 전 사진을 보고 맞춰야 한다. `description`은 사진을 바꾸지 않고 `[LOADTEST:<run_id>:<sequence>] 자동 생성 테스트 제보` 형식으로 만든다.

### 계정 수 계산

계정당 제보 간격이 C초이고 목표 제보량이 R건/초이면, 이론상 최소 계정 수는 `ceil(R × C)`다. 요청 지연과 스케줄 오차를 고려해 초안에서는 20% 여유를 둔다.

| 목표 제보량 | C=5초일 때 최소 | 20% 여유 적용 |
|---|---:|---:|
| 초당 1건 | 5개 | 6개 |
| 초당 5건 | 25개 | 30개 |
| 초당 10건 | 50개 | 60개 |
| 초당 20건 | 100개 | 120개 |

이는 처리량 보장이 아닌 계정 간격의 하한 계산이다. 계정별 동시 제출은 1개로 제한하며, 이전 요청 완료 후 C초 이상 기다리는 보수적 발송 정책에서는 응답 지연만큼 추가 계정이 필요하다. 목표 부하를 내지 못하면 계정 부족·동시성 부족·생성기 병목을 결과에 표시한다.

계정 가입과 운영자 지정은 준비 단계에서 수행한다. 회원가입·로그인 폭증이 제보 성능 측정에 섞이지 않게 한다. NCP 운영 환경에서는 로컬 데모 계정이 있다고 가정하지 않는다.

## 4. 요청·처리 흐름

1. **계획 확인:** URL, 파일, 계정 수, 목표 요청 수·바이트 수·실행 한도를 검사한다. `plan`은 로컬 입력만 검사하고 요청을 보내지 않는다.
2. **사전 점검:** health/config API 확인 → 계정 로그인 및 역할 확인 → 좌표 resolve → 테스트 제보 1건 접수. 이 단계는 실제 데이터를 만들며 측정 구간과 분리한다.
3. **준비:** 사진·좌표·계정 배정과 각 요청의 설명·멱등 키를 결정한다. 입력값 및 난수 seed를 기록한다.
4. **부하 발생:** 단계별 도착률에 맞춰 새 요청을 발송한다. 피드와 제보 각각 독립적인 속도와 동시성 한도를 사용한다.
5. **상태 관측:** 반환된 제보 ID를 표본 추출해 상태를 제한된 속도로 조회한다. 관측 부하는 주 테스트 부하와 따로 집계한다.
6. **드레인:** 신규 제보 발송을 멈추고 진행 중 요청과 AI 대기를 정해진 시간까지 관측한다. 낮은 피드 조회는 유지할 수 있다.
7. **결과 저장:** 실제 발송량, 요청 결과, 생성 ID, 미확정 요청, 지연과 상태 분포를 기록한다. NCP 콘솔 자료와 대조한다.

`POST /api/reports` 필드: `photo`, `stage`, `species`, `latitude`, `longitude`, `description`, `photo_source=upload`, `location_source=manual`. `zone_id`는 생략하고 서버가 좌표로 판정하게 한다. 좌표 분포는 구별 균등 분산을 기본으로 하고, 한 구 집중 시나리오를 별도로 둔다.

인증은 `Authorization: Bearer <token>`, 멱등 키는 논리 제보마다 고유한 `Idempotency-Key: <run_id>:<sequence>`를 사용한다. 요청마다 새 제보를 만들되 동일 요청을 재전송할 경우 키와 모든 입력을 유지한다.

### 오류와 재시도

- 쓰기 재시도 기본값은 0회다. 타임아웃·503은 DB 저장 후 발생할 수 있으므로 새 키로 무작정 재등록하지 않는다.
- 응답이 불확실한 제출은 키·계정 식별자·설명 표식으로 manifest에 남기고, 별도의 사후 확인 대상으로 분류한다. 현재 API에는 멱등 키 전용 조회가 없으므로 내 제보 목록 등으로 제한적으로 대조하며, 찾지 못했다고 미생성을 확정하지 않는다.
- 429는 제보 간격 제한, 401/403은 인증·권한, 413/422는 사진·입력 문제로 구분한다. 429를 서버 과부하 오류나 성공 처리량에 포함하지 않는다.
- AI의 `REJECTED`는 HTTP 요청 실패와 다르다. `REVIEW`는 자동 검증 처리 후 운영자 검토가 필요한 상태이며 공개 승인이 아니다.
- 포화된 생성기는 무제한으로 로컬 큐를 쌓거나 지연된 요청을 한꺼번에 몰아 보내지 않는다. 발송하지 못한 예약 슬롯을 `dropped`로 기록한다.
- 자동 재로그인은 계정별로 1개만 실행하고, 인증 트래픽을 별도 기록한다. 지속적인 인증 오류는 테스트 설정 실패로 처리한다.

## 5. 초안 부하 시나리오

다음 수치는 실행 제안이며 서버 성능이나 확장 임계값을 보장하지 않는다. 실제 확장 정책의 평가 시간과 서버 기동 시간을 반영해 조정한다.

| 단계 | 시간 | 제보/초 | 피드 조회/초 | 목적 |
|---|---:|---:|---:|---|
| 소규모 점검 | 60초 | 1 | 2 | 입력과 실제 접수·검증 경로 확인 |
| 준비 부하 | 120초 | 2 | 10 | 초기 상태와 기준 응답 시간 확보 |
| 증가 1 | 180초 | 5 | 25 | 확장 조건 접근 여부 관측 |
| 증가 2 | 300초 | 10 | 50 | 확장과 신규 서버 편입 관측 |
| 감소·드레인 | 300초 | 0 | 5 | 대기 해소와 응답 회복 관측 |

전체 실행은 제보 최대 4,200건(사전 점검 제외), 피드 목록 조회 22,320회다. 상태 조회·이미지 다운로드·인증은 별도다. 처음에는 소규모 점검만 실행한 뒤, 전체 계획의 비용·계정·한도를 맞춘다. 이 초안에는 최대 제보 4,500건을 한도로 둔다.

순간 폭증은 별도 시나리오로 준비한다. 예를 들어 낮은 부하에서 30초간 제보 20건/초로 올린 뒤 복귀한다. 짧은 폭증이 실제 정책 평가 시간을 채우지 못하면 확장이 일어나지 않을 수 있으므로, 지연 내성과 자동 확장 검증 결과를 구분한다.

피드 조회는 최신순/인기순을 70:30, 전체/구별을 50:50으로 섞는 초안을 사용한다. 조회 가능한 데이터가 있는 1~5페이지에서 선택하고 페이지 크기는 기본 12로 둔다. 이미지 다운로드는 기본 꺼짐이며 켜면 성공한 목록 응답 중 지정 비율에서 사진 1장만 받는다. 서명 URL은 실행 중 받은 것을 사용하고 로그에 토큰을 기록하지 않는다.

상태 관측은 접수된 ID의 10% 표본을 최대 100개까지 추적하고, 5초 간격·전체 최대 5회/초로 제한한다. 이 값은 조정 가능하다. `APPROVED`, `REJECTED`, `REVIEW`, `UPLOAD_FAILED`이면 자동 검증 관측을 종료한다. 드레인 제한 이후 대기는 미완료로 남긴다.

피드 노출 확인은 승인된 표본을 대상으로 수행한다. 최신순 첫 페이지만 보고 없다고 실패 처리하지 않는다. 실행 중인 생성량에 맞춰 페이지 탐색 범위를 정하고 범위를 넘으면 `visibility_unknown`으로 남긴다. 노출 지연은 폴링 주기에 따른 관측 오차를 함께 표시한다.

## 6. 계측과 자동 확장 판정

| 영역 | 기록 항목 |
|---|---|
| 요청 | 목표·실제 발송 RPS, 완료 RPS, 미발송 수, 진행 중 수, 상태 코드, 타임아웃 |
| 지연 | API별·단계별 p50/p95/p99, 요청 수, 성공/실패 구분 |
| 데이터 | 접수 고유 ID 수, 승인·검토·반려·업로드 실패·미확정·대기 수 |
| 비동기 | 접수 응답 후 검증 결과 관측까지의 시간, 드레인 종료 시 남은 대기 |
| 피드 | 목록 응답 지연, 승인 표본의 노출 확인, 선택적 사진 다운로드 시간·바이트 수 |
| 생성기 | CPU·메모리·네트워크, 계정 대기, 동시성 한도, 발송 지연·dropped |
| NCP | 실제 감시 지표, 임계값 충족 시각, 확장 이벤트, 서버 수, LB 정상 대상 수 |
| 의존 서비스 | 가능한 범위의 DB 연결·잠금·CPU, Object Storage 오류, 함수 실행·오류, CLOVA 지연·제한 |

자동 확장 판정은 **실제 정책 조건 충족 → 확장 이벤트 → 서버 수 증가 → LB 정상 대상 편입 → 확장 후 응답·처리량**의 시간 순서를 대조한다. 클라이언트 응답만으로 어느 서버가 요청을 처리했는지는 단정하지 않으며 LB/서버 로그로 보완한다.

조건을 충족하지 않았거나 최대 서버 수에 이미 도달했다면 확장 미발생을 설정 실패로 단정하지 않는다. API 서버 확장과 검증 워커/Cloud Functions의 병렬 처리는 별개다. API가 빨라져도 AI·DB가 병목이면 검증 대기는 계속 늘어날 수 있다. Scale-in은 별도 충분한 저부하 관측 구간을 두며 300초 드레인만으로 반드시 발생한다고 보지 않는다.

초안 성능 목표는 정상 입력 접수 성공률 99% 이상, 업로드 p95 2초 이하, 피드 목록 p95 500ms 이하로 둔다. 이는 서비스 보장값이나 측정 결과가 아니며 사진 크기·네트워크·배포 사양에 따라 확정한다. AI 승인률은 사진 분류 결과이므로 API 성공률과 합치지 않는다.

## 7. 실행 한도와 데이터 관리

- 최대 지속 시간·제보 수·바이트 수·동시성을 설정하고 어느 한도든 도달하면 신규 발송을 멈춘다. 피드 전용 모드도 시간·요청 수 한도를 둔다.
- 초안 중단 조건: 최근 30초에 완료 표본 20개 이상인 측정 API에서 5xx+타임아웃이 10% 이상. 429 급증은 별도 설정 문제로 표시하고 해당 쓰기 단계를 중단한다. 정책은 설정으로 변경 가능하다.
- Ctrl+C 시 신규 발송을 즉시 멈추고, 정해진 짧은 종료 대기 후 부분 결과를 저장한다. 테스트 실패나 중단도 결과 파일을 남긴다.
- CLOVA 호출은 작업 재시도로 제보 수보다 많아질 수 있고, 생성기 종료 뒤에도 이미 접수된 검증과 비용은 계속 발생할 수 있다. 클라이언트 한도는 클라우드 전체 비용의 강제 상한이 아니다.
- 모든 제보에 실행 표식을 넣고 생성 계정·제보 ID·요청 키를 manifest에 보관한다. 승인되면 피드·지도 집계·포인트에 실제로 반영된다. 가능하면 별도 테스트 DB·사진 버킷을 연결한 배포를 대상으로 한다.
- 현재 공개 API에는 제보 삭제 기능이 없다. 1차 구현은 삭제 목록 생성까지 제공하며 자동 삭제하지 않는다. 정리 기능은 별도 서버 관리 명령으로 설계하고 테스트 데이터만 대상으로 한다.
- 정리 범위에는 사진 객체·검증 작업·검증 이력·좋아요·포인트 내역·구역 재집계가 포함된다. 기존 `reset-showcase`가 신규 부하 테스트 계정을 정리해 준다고 가정하지 않는다. 정리 전 남은 이벤트·워커 작업의 종료도 확인한다.

## 8. 구현 산출물과 인터페이스

구현 초안은 별도 Python CLI와 비동기 HTTP 클라이언트로 구성한다. 서버 API 계약과 운영 제보 정책은 변경하지 않는다. 구체적인 라이브러리 버전은 구현 시 프로젝트 런타임에 맞춰 고정한다.

예정 파일:

- `scripts/load_test.py`: 계획 검사, 사전 점검, 부하 실행, 결과 기록
- `scripts/loadtest/scenarios.example.json`: 단계·속도·한도 예시
- `scripts/loadtest/photos.example.json`, `locations.example.json`: 사진·위치 매니페스트
- `scripts/requirements-loadtest.txt`: 테스트 클라이언트 의존성
- `artifacts/loadtest/<run_id>/summary.json`: 비밀 값 없는 설정, 집계, 종료 사유
- `artifacts/loadtest/<run_id>/requests.jsonl`: 요청별 시간·API·상태·지연. 이미지·JWT·비밀번호·서명 URL 제외
- `artifacts/loadtest/<run_id>/manifest.json`: 생성 데이터 및 불확실 제출 추적
- `artifacts/loadtest/<run_id>/report.md`: 단계별 결과와 NCP 수동 관측 자료를 대조할 표

다음은 **구현 예정 인터페이스**이며 현재 실행 가능한 명령이 아니다.

```bash
# 네트워크 요청 없이 로컬 입력과 예상 발송량 확인
python scripts/load_test.py plan --scenario scripts/loadtest/scenarios.example.json

# 계정 등 비밀 값은 커밋하지 않는 별도 파일 경로로 전달
python scripts/load_test.py run \
  --base-url https://api.example.com \
  --mode mixed \
  --accounts-file /private/path/loadtest-accounts.json \
  --photos-file scripts/loadtest/photos.example.json \
  --locations-file scripts/loadtest/locations.example.json \
  --scenario scripts/loadtest/scenarios.example.json
```

1차 구현은 단일 생성기다. 해당 장비가 목표 RPS를 내지 못하는 경우에만 분산 실행을 추가 설계한다. 여러 생성기를 실행할 때는 계정 풀·run ID·한도를 분리해야 한다.

## 9. 구현 완료 기준

1. 계획 검사만으로 예상 제보 수·계정 필요량·발송 바이트 수·설정 누락을 확인할 수 있다.
2. 소규모 테스트에서 실제 API에 제보가 생성되고, 요청 키와 생성 ID가 결과에 남는다.
3. 202 접수 성공과 검증 결과·피드 공개를 별도 지표로 제공한다.
4. 계정 간격을 지키면서 목표 도착률을 발생시키고, 불가능하면 목표 미달을 숨기지 않는다.
5. 중단·타임아웃·503에서도 결과와 미확정 요청 정보가 남고 중복 제보를 무작정 만들지 않는다.
6. 테스트 결과에 API별·단계별 처리량과 지연, 429/5xx/입력 오류, 대기 잔량이 포함된다.
7. NCP의 확장 정책·이벤트·LB 편입 자료를 넣을 자리가 있고, 자료가 없으면 자동 확장 확인을 미검증으로 표시한다.
8. 기존 데이터와 혼동되지 않는 실행 표식·정리 목록을 제공하며 비밀 값은 결과물에 포함하지 않는다.

## 10. 구현 전에 확정할 사항

- 실제 LB API 주소와 부하 발생 장비
- 운영 배포 또는 별도 테스트 배포 중 대상, 테스트 데이터의 노출·정리 방식
- 테스트 운영자 계정 풀과 실제 제보 간격 설정
- 저장소 샘플로 시작할지, 실제 사진으로 AI 검증까지 측정할지
- 목표 제보/조회 RPS, 사진 크기 분포, 최대 실행 건수와 시간
- 현재 NCP 확장 조건과 관측·비용 한도

명세서 작성 단계에서는 위 값이나 사진을 추가로 전달하지 않아도 된다. 구현 시 예시 설정과 로컬 소규모 검증부터 진행하고, 실제 NCP 부하 실행 전 대상별 값을 채운다.
