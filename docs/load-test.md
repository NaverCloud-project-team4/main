# 사진 제보 자동 생성 및 부하 테스트 실행

사진 7장 중 하나를 무작위로 골라 실제 API에 제보한다. 은행 사진 3장은 `GINKGO`, 단풍 사진 3장은 `MAPLE`로 전송한다. 추가한 우사기 캐릭터 1장은 무관 이미지 반려 검증용으로 `MIXED`를 전달하고 기대 결과를 `REJECTED`로 기록한다. 기대 결과는 서버에 전송하거나 강제하지 않는다. 로컬 demo 검증은 이 사진도 기본 `REVIEW`이며 실제 반려 여부는 CLOVA 환경에서 확인한다. 단계는 모두 `PEAK`로 설정되어 있고 `scripts/loadtest/photos.example.json`에서 바꿀 수 있다.

위치는 매번 **서울 자치구를 균등 무작위 선택한 다음 그 구의 실제 경계 안에서 무작위 좌표를 생성**한다. 구 면적에 비례한 추출은 아니다. 실행 시 서버가 제공하는 활성 자치구 경계를 사용하고 각 구의 좌표를 resolve API로 대조한다. 사진의 실제 촬영 장소를 재현하는 것은 아니며 모든 설명에 `[LOADTEST:실행ID:번호]`를 붙인다.

## 준비

프로젝트 루트에서 Python 3.12 이상의 환경을 사용한다. 기존 `.venv`에는 필요한 라이브러리가 있다. 새 클라이언트 환경이라면:

```bash
python -m pip install -r scripts/requirements-loadtest.txt
```

HTTP 부하 생성에는 NCP 관리 키가 필요 없다. API와 사진 데이터, 테스트 계정만 사용한다. 생성기는 서버와 별도 장비에서 실행하고 `--base-url`은 사용자가 접근하는 LB 경유 API 주소로 지정한다. `/api`는 붙이지 않는다.

### 테스트 계정 만들기

현재 API는 파일 업로드와 수동 좌표를 운영자에게 허용하므로 **테스트 전용 운영자 계정**을 사용한다. 일반 사용자 계정으로 실행하면 업로드 전에 중단된다. 회원가입이나 권한 부여를 측정 구간에 섞지 않는다.

대상 API와 같은 DB 환경설정이 있는 **백엔드 장비**에서 아래 관리 명령으로 준비할 수 있다. 백엔드 의존성과 DB 마이그레이션이 먼저 준비되어 있어야 한다. 기존 사용자는 수정하지 않으며 새 `loadtest-...@example.com` 계정만 만든다.

```bash
# 로컬 기본 테스트: 2개. 파일이 이미 있으면 덮어쓰지 않는다.
.venv/bin/python scripts/prepare_loadtest_accounts.py \
  --count 2 --output .data/loadtest-accounts.local.json

# 전체 부하 예시의 계정 풀: 다른 출력 파일로 생성
.venv/bin/python scripts/prepare_loadtest_accounts.py \
  --count 60 --output .data/loadtest-accounts.ncp.json
```

NCP 계정 준비 명령은 NCP DB를 가리키는 기존 백엔드 환경에서 실행해야 한다. 로컬 기본 설정으로 실행한 계정은 로컬 DB에만 생긴다. 생성한 파일은 부하 생성 장비에 비공개로 전달한다. 파일 권한은 `0600`이며 Git에서 제외된다. 기존 테스트 운영자 계정이 있다면 다음 형태로 파일을 준비해도 된다.

```json
[
  {"email": "실제 테스트 이메일", "password": "실제 테스트 비밀번호"}
]
```

기본 제보 간격은 계정당 5초다. 시나리오의 `cooldown_seconds`를 **배포 서버의 실제 `REPORT_COOLDOWN_SECONDS` 값**에 맞춘다. 서버는 현재 이 값을 공개 config API로 내려주지 않으므로 자동 확인하지 않는다. 계정당 동시에 1건만 전송하고 응답 완료 후 설정한 간격을 기다린다. 초당 10건에는 이론상 50개 이상, 지연 여유를 둔 예시에는 60개를 사용한다.

## 먼저 계획 확인

`plan`은 파일을 읽고 검사할 뿐 네트워크 요청이나 데이터 생성을 하지 않는다. 계정 파일은 생략 가능하다.

```bash
# 기본값: 사진 7장, 12초 소규모 테스트
.venv/bin/python scripts/load_test.py plan

# 명세서의 전체 증가 시나리오
.venv/bin/python scripts/load_test.py plan \
  --scenario scripts/loadtest/scenarios.example.json \
  --accounts-file .data/loadtest-accounts.ncp.json
```

계획에는 목표 제보/요청 수, 최소 계정 수, 사진 형식·해상도·해시, 최대 원본 사진 바이트 예상량이 표시된다. `max_upload_bytes`는 **사진 파일 바이트** 한도이며 multipart·HTTP·TLS의 실제 총 전송량과 다르다.

## 소규모 실행

로컬 개발 서버가 켜져 있는 상태에서:

```bash
.venv/bin/python scripts/load_test.py run \
  --base-url http://127.0.0.1:8000 \
  --accounts-file .data/loadtest-accounts.local.json
```

기본 시나리오는 사전 점검 제보 1건과 측정 제보 2건, 피드 조회 12회를 목표로 한다. 실제 API를 호출해 사진과 DB 데이터를 만든다. 로컬 demo 모드에서는 `demo_outcome`을 강제하지 않으므로 검증 결과가 `REVIEW`로 남는 것이 정상이며 공개 피드에는 나오지 않는다. NCP production에서는 기존 CLOVA 경로로 검증되고 승인된 제보만 공개된다.

사전 점검에는 로그인·역할 확인, 서버 설정, 활성 구 경계, 구별 좌표 판정, 1건의 실제 제보 접수가 포함된다. 그 후 측정 구간이 시작된다. 사전 제보도 최대 건수·사진 바이트 한도에 포함되지만 측정 RPS에는 포함되지 않는다.

## NCP 전체 시나리오

### 실시간 화면으로 보기

생성기와 **같은 장비**의 별도 터미널에서 아래 명령을 실행한 뒤 브라우저에서 `http://127.0.0.1:8765`를 연다.

```bash
.venv/bin/python scripts/loadtest_dashboard.py
```

다른 터미널에서 기존 `load_test.py run ...` 명령을 실행하면 새 실행을 자동으로 따라가며 1초마다 갱신한다. 생성기가 NCP API를 대상으로 실행 중이어도 결과 파일이 이 장비에 있으면 같은 방식으로 볼 수 있다. 생성기가 원격 장비에 있다면 대시보드도 그 장비에서 실행하고 SSH 포트 포워딩 등으로 접속한다. 대시보드 서버는 로컬 루프백에만 바인딩한다.

화면에는 접수 건수, 최근 관측된 승인·대기·검토 상태, 오류, 최근 요청 속도, 서울 제보 위치와 사진 목록이 표시된다. 은행·단풍 필터와 과거 실행 선택을 제공한다. 지도는 최근 1,000건, 사진 목록은 최근 40건까지 표시한다. 공개 승인을 기다리지 않고 접수 기록부터 표시하므로 검토·반려 제보도 확인할 수 있다.

이 화면은 생성기의 로컬 `live.json`만 읽는다. API 서버나 AI에 추가 요청하지 않으며 NCP 서버 수·CPU·오토 스케일링은 수집하지 않는다. AI 상태는 기존 표본 조회 정책에 따른 최근 값이며, 표본 밖의 제보는 접수 시점 상태로 표시한다. 생성기가 종료되면 마지막 결과를 보여주고, 비정상 종료로 갱신이 끊기면 갱신 지연으로 표시한다.

기존 실행 결과도 `summary.json`과 `manifest.json`에서 읽어 볼 수 있다. 앞으로 실행하는 생성기는 `live.json`과 로컬 사진 미리보기를 자동으로 저장한다. 별도 결과 경로를 썼다면 대시보드에도 `--results-dir <같은 결과 경로>`를 전달한다. `--port`로 화면 포트를 바꿀 수 있다.

### 실제 NCP 요청 실행

실제 주소와 대상 서버에서 준비한 계정 파일로 실행한다.

```bash
.venv/bin/python scripts/load_test.py run \
  --base-url https://YOUR-API-DOMAIN \
  --accounts-file .data/loadtest-accounts.ncp.json \
  --scenario scripts/loadtest/scenarios.example.json \
  --mode mixed
```

전체 예시는 960초 동안 제보 목표 4,200건, 피드 조회 22,320회이며 사전 제보 1건은 별도다. 최대 제보 4,500건·측정 예약 요청 30,000회·원본 사진 2 GiB·측정 1,000초 한도를 둔다. 상태 조회·인증·선택적 사진 다운로드는 별도 제한으로 동작한다. 사전 점검 시간, 진행 중 요청 종료 대기, 검증 드레인, 최종 피드 확인은 측정 시간 밖이다.

제보는 초당 1 → 2 → 5 → 10건으로 늘어난다. 마지막 단계에서는 제보를 멈추고 피드 조회만 유지한다. 종료 후 표본에 미완료 검증이 남으면 `drain_seconds`까지 추가로 관측한다. 순간 폭증을 보려면 시나리오를 복사해 단계의 `seconds`와 RPS를 바꾼다. 짧은 폭증은 실제 확장 정책의 평가 시간을 채우지 못할 수 있다.

### 주요 옵션

| 옵션 | 설명 |
|---|---|
| `--mode submit` | 사진 제보만 발송 |
| `--mode feed` | 로그인·사진·사전 제보 없이 피드 조회만 발송 |
| `--mode mixed` | 제보와 조회를 독립적인 속도로 발송, 기본값 |
| `--district seongdong` | 특정 구에 집중. 생략하면 활성 서울 구 전체에서 무작위 |
| `--seed 42` | 사진·위치 선택 난수. 같은 입력과 실행 순서에서 재현 가능 |
| `--photos-file` | 사진 매니페스트 경로. 사진의 상대 경로는 매니페스트 폴더 기준 |
| `--scenario` | 부하 단계·간격·한도 설정 JSON |
| `--output-dir` | 결과 폴더의 상위 경로, 기본 `artifacts/loadtest` |

초기 명세서의 고정 좌표 파일 대신 실제 활성 경계를 받아 무작위 좌표를 생성하므로 `--locations-file`은 필요하지 않다. `--district`에는 영문 ID·구 코드·구 이름을 사용할 수 있다.

피드 조회는 최신순/인기순 70:30, 전체/구별 50:50을 사용한다. 처음에는 1페이지를 조회하고, 응답의 전체 건수를 학습한 조합부터 존재하는 1~5페이지를 무작위로 선택한다. 사진 다운로드를 포함하려면 `photo_download_ratio`를 0~1 범위로 설정한다. 한 목록당 최대 사진 1장, `image_max_bytes`를 넘으면 중단하며 API JWT를 사진 서버에 전달하지 않는다.

## 중단과 오류

- Ctrl+C로 새 발송을 멈추고 `shutdown_seconds` 안에서 진행 중 요청을 마친 뒤 결과를 저장한다.
- 목표 속도를 못 내면 로컬 큐에 쌓거나 뒤늦게 폭증시키지 않고 `dropped`로 남긴다. 한 계정으로 높은 RPS를 설정해도 제한을 우회하지 않는다.
- 한도 도달은 정상 종료 사유로 기록된다. 429, 인증·입력 오류는 실행을 중단한다. API별 최근 30초 완료 표본이 20개 이상이고 5xx/통신 오류 비율이 10% 이상이어도 중단한다.
- 사진 제보는 자동 재시도하지 않는다. 타임아웃·503은 이미 DB에 저장되었을 수 있어 `UNCERTAIN`으로 남긴다. 새 키로 재등록하지 말고 해당 실행 표식과 계정으로 사후 대조한다.
- 이미 접수된 AI 검증은 생성기를 종료해도 계속 실행될 수 있다. 클라이언트의 건수·바이트 한도가 CLOVA 전체 비용을 강제로 제한하지는 않는다.

종료 코드 0은 계획한 실행 또는 한도 종료, 1은 설정/런타임/오류 임계값 중단, 130은 사용자 중단이다. 실행 성공이 성능 목표 충족이나 오토 스케일링 성공을 의미하지 않는다.

## 결과 확인

실행마다 `artifacts/loadtest/<UTC실행ID>/`가 생성된다.

| 파일 | 내용 |
|---|---|
| `report.md` | 발송·성공·RPS·p95 요약, NCP 관측 기록 표 |
| `summary.json` | 단계별·API별 지연/오류/실제 RPS, 목표 판정, 생성기 자원 사용 |
| `requests.jsonl` | 요청별 시각·분류·상태 코드·지연. URL 토큰·본문·비밀번호 제외 |
| `manifest.json` | 생성 제보 ID·계정 ID·서울 좌표·사진 매핑·미확정 요청·관측 결과 |
| `manifest.jsonl` | 제출 직전과 응답 후 기록을 즉시 추가하는 복구용 저널 |
| `live.json` | 1초 간격의 화면용 현황·최근 제보·60초 요청 흐름 |
| `photos/` | 화면에 표시할 로컬 사진 미리보기. 실행에 사용한 원본 파일 복사본 |

업로드 202는 접수 성공이다. AI의 승인·검토·반려는 별도 상태다. `last_known_report_states`는 전체 제보의 마지막으로 아는 상태이고, 표본 밖의 제보에는 접수 당시 상태가 남는다. 검증 지연은 표본에서 접수 응답 후 종결 상태를 **관측할 때까지**의 시간이며 폴링 오차를 포함한다.

기본 전체 시나리오는 10% 표본을 최대 100개까지, 전체 최대 5회/초로 관측한다. 승인된 표본의 공개 여부를 최신순 최대 5페이지×50건에서 최종 확인한다. 탐색 범위 안에 없으면 `visibility_unknown`으로 남기며 공개 실패로 단정하지 않는다.

성능 목표는 초안의 성공률 99%·업로드 p95 2초·피드 p95 500ms로 `draft_objectives`에 기록한다. 실제 목표 부하가 충분히 전달됐는지는 `scheduled`, `dropped`, 실제 RPS도 함께 확인한다. 자원 사용의 RSS 단위는 macOS 바이트, Linux KiB다. 원본 업로드 바이트와 선택적 사진 다운로드 바이트를 기록하며 OS 전체 네트워크 측정값은 아니다.

**자동 확장 성공 여부는 자동 판정하지 않는다.** NCP 콘솔의 지표 임계값 충족 → 확장 실행 이력 → 서버 증가 → LB 정상 대상 편입 시각을 결과의 UTC 단계 시각과 대조한다. API 서버와 AI 검증 처리 용량은 별도다.

## 데이터 정리

승인된 제보는 실제 피드·지도·포인트에 반영되므로 별도 테스트 배포를 사용할 수 있다. 현재 공개 API에는 제보 삭제가 없다. `manifest.json`과 `manifest.jsonl`은 정리 대상을 추적하지만 자동 삭제하지 않는다. 기존 `reset-showcase`는 이 생성기의 데이터 정리에 사용하지 않는다.

정리 관리 작업에서는 해당 실행의 사진 객체·검증 작업·이력·좋아요·포인트·테스트 계정을 처리하고 구역 집계를 다시 계산해야 한다. 대기 이벤트·워커 처리 중 삭제하면 충돌할 수 있으므로 작업 종료부터 확인한다. 불확실 제출은 해당 계정의 내 제보 목록과 실행 표식을 대조하고 조회에서 못 찾았다는 이유만으로 미생성을 확정하지 않는다.
