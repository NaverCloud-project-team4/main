## 1 서비스 개요와 현재 상태

까우룽까우룽은 서울의 단풍 사진 제보를 지도와 피드로 공유하는 서비스입니다. 사용자는 현재 위치에서 사진을 촬영해 제보하고, 승인된 사진에 좋아요를 누릅니다. 지도는 구별 단풍 상태와 지역 관심도를 함께 보여줍니다.

팀 공유 기준은 2026년 10월 23일 통합 커밋 2d444a1입니다. 팀 main의 febb943에 포함된 DB·예측·집계 기능과 기존 지도·촬영 UI를 합쳤습니다. 작업 브랜치는 codex/current-location-reports이며 이 문서가 main 병합이나 클라우드 배포 완료를 의미하지는 않습니다.

| 영역 | 현재 구현 |

### 팀원이 먼저 알아둘 사항

- 로컬 기능 검증은 완료했습니다. 실제 관리형 MySQL·Object Storage·CLOVA·Cloud Functions의 통합 검증은 남아 있습니다.
- 팀원의 서버 API·DB 연결 성공은 공유받은 상태이며, 이번 문서 작성 과정에서 해당 원격 서버를 직접 점검하지는 않았습니다.
- local 모드의 demo 검증은 실제 사진 내용을 판별하지 않습니다. 제보 승인 흐름과 AI 정확도 검증을 구분해야 합니다.

## 2 전체 구조와 배포 목표

현재 로컬에서는 프론트 개발 서버와 API, 검증 워커가 실행됩니다. API는 HTML을 제공하지 않고 JSON과 권한을 검사한 사진 조회를 담당합니다. 현재 프론트는 /api/zones를 직접 조회합니다. 지도 JSON을 CDN에서 읽는 프론트 경로는 별도 연결 대상입니다.

```text
현재: 브라우저 → React/Vite → FastAPI → DB
                         ↘ 로컬 사진 저장소
       검증 워커 ↔ DB 작업 큐 → demo 또는 CLOVA → 결과·집계

목표: 브라우저 → Global Edge → 정적 웹 Object Storage
      브라우저 → Public ALB → Private FastAPI → Private MySQL
                              ↕ 검증 워커 또는 Cloud Functions
                              ↕ 비공개 사진 저장소·CLOVA
```

### 네이버 클라우드 배포 목표

- 정적 프론트는 빌드한 frontend/dist의 내용을 정적 웹용 Object Storage에 올리고 Global Edge로 제공합니다. Global Edge 자체에 소스 코드를 실행하는 구조는 아닙니다.
- 브라우저의 API 요청은 Public Load Balancer Subnet의 ALB를 거쳐 Private App Subnet의 FastAPI로 전달합니다.
- Cloud DB for MySQL은 별도 DB용 Private Subnet으로 분리하고 API·워커에서만 접근하도록 구성합니다. DB 주소는 프론트에 노출하지 않습니다.
- 사진은 비공개 Object Storage에 저장합니다. 공개 지도 JSON용 MAP_BUCKET과 정적 프론트 저장소의 용도를 구분합니다.
- 검증은 상시 워커 또는 Object Storage 트리거 Cloud Functions로 실행합니다. 복구·집계 스케줄도 별도로 연결해야 합니다.

이 구성은 배포 목표입니다. LB·ACG·NAT·HTTPS·Auto Scaling 등 실제 리소스 설정과 연결 검증은 담당자가 진행해야 합니다.

## 4 사진 제보와 검증의 데이터 흐름

### 사진 한 건이 반영되는 과정

- 1  로그인 후 사진 제보 화면 진입 → 현재 위치 수집 → POST /api/zones/resolve로 서울 구 자동 분류.
- 2  일반 사용자는 카메라 프레임을 JPEG로 촬영합니다. 운영자는 파일 선택 또는 카메라 촬영과 수동 위치 지정을 사용할 수 있습니다.
- 3  multipart/form-data로 POST /api/reports 요청. JWT와 Idempotency-Key를 전달합니다.
- 4  API가 역할·입력·이미지·좌표·제보 간격을 검사하고, DB에 제보와 WAIT_UPLOAD 작업을 먼저 저장합니다.
- 5  사진을 저장소에 올린 뒤 제보를 PENDING_AI로, 작업을 READY로 바꾸고 202를 반환합니다. 저장이 불확실하면 DB 기록을 복구 대상으로 남깁니다.
- 6  워커가 임대 토큰으로 작업을 선점하고 사진을 가져와 demo 또는 CLOVA 판별을 실행합니다.
- 7  APPROVED·REVIEW·REJECTED 결과를 DB에 기록합니다. 처음 승인될 때만 포인트 원장과 사용자 잔액에 20P를 반영합니다.
- 8  프론트가 상태를 조회하고 피드·내 제보를 갱신합니다. 구별 단풍 상태와 관심도는 다음 1분 집계에 반영됩니다.

### 상태와 오류 처리

```text
PENDING_UPLOAD → PENDING_AI → APPROVED / REVIEW / REJECTED
PENDING_UPLOAD → UPLOAD_FAILED
REVIEW → 운영자 승인 또는 반려
```

검증 오류는 기본 재시도 설정에 따라 재처리하고 3회 오류 후 운영자 검토로 보냅니다. 작업 임대 토큰으로 늦게 도착한 이전 실행 결과가 새 결과를 덮지 못하게 합니다. 동일 요청 키와 같은 내용은 같은 제보를 반환하고, 내용이 다르면 409입니다.

### 사진과 위치의 신뢰 범위

일반 사용자 화면에는 파일 입력과 임의 위치 선택이 없습니다. 서버는 upload/manual을 운영자에게만 허용하지만 camera/current 값은 브라우저의 신고값입니다. 현재 구조는 실제 현장 촬영이나 위치 위변조 방지를 증명하지 않습니다. 사진은 EXIF/GPS 제거와 크기 정규화를 거칩니다.

## 5 단풍 상태와 지도 관심도 정책

단풍 상태와 지역 관심도는 서로 다른 데이터입니다. 지도 영역 색과 나무 크기는 관심도를 나타냅니다. GREEN·STARTING·PEAK·FALLEN은 구의 단풍 상태이며, 좋아요가 사진의 진위나 단풍 단계를 결정하지 않습니다.

### 구별 단풍 상태

- 최근 3일 안 승인 제보 중 최신 10건을 사용합니다. 3건 이상이면 다수결로 단계를 정하고 동률이면 가장 최근 제보의 단계를 사용합니다. source는 REPORT입니다.
- 제보가 부족하면 구 안 예측 지점의 예상 절정일 평균을 사용합니다. 지점이 없으면 기본 예상 절정일을 사용합니다. source는 FORECAST입니다.
- 예측일 기준 d = 오늘 − 예상 절정일입니다. d ≤ −14는 GREEN, −14 < d < −3은 STARTING, −3 ≤ d ≤ 3은 PEAK, d > 3은 FALLEN입니다.
- 코드 기본 절정일은 2026-10-31이며 FORECAST_TODAY로 시연 날짜를 고정할 수 있습니다. 매 시즌 예측 자료와 날짜 설정의 갱신이 필요합니다.

### 지역 관심도와 지도 표현

```text
관심 점수 = 승인 제보 수 × 2 + 서로 다른 제보자 수 × 3 + 좋아요 수
집계 범위 = 최근 7일에 생성된 승인 제보
```

| 단계 | 관심 점수 | 구역 색 | 나무 |
| --- | --- | --- | --- |
| 0 | 0 | 노랑  #facc15 | 없음 |
| 1 | 1–14 | 주황  #fb923c | 작은 나무 60px |
| 2 | 15–39 | 진한 주황  #ea580c | 중간 나무 78px |
| 3 | 40 이상 | 빨강  #dc2626 | 큰 나무 96px |

나무 크기는 데스크톱 기준이며 작은 지도에서는 줄어듭니다. 입체감 있는 투명 이미지 마커를 구 중심에 놓는 방식입니다. 구 선택은 파란 테두리로 표시하고 관심도 색은 유지합니다.

### 지도 설정

네이버 GL 모드와 Style Editor ID 2ca6dae8-1af8-4390-b762-6f2736423d59를 공유합니다. SDK는 ID에 연결된 발행본을 사용하며 별도 버전 옵션은 넣지 않습니다. 서울 외부는 가리고 이동을 제한합니다. 경계 자료는 SGIS 기반 2026-10-01 자료이며 출처와 라이선스를 화면·저장소에 표시합니다.

집계는 1분 주기이고 지도 화면도 60초마다 구 목록을 갱신합니다. 각 주기가 어긋나면 화면에는 추가 지연이 생길 수 있습니다. 새로고침으로 현재 집계 결과를 다시 읽을 수 있습니다.

## 7 팀원 로컬 실행 안내

준비 환경은 Python 3.12 이상, Node.js 24, pnpm 11입니다. 명령어는 저장소 루트 기준입니다. 이미 실행 중인 API가 있다면 프론트만 별도로 띄울 수 있습니다.

### 새 환경에서 전체 실행

```text
python3.12 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements-dev.txt
cd frontend
pnpm install --frozen-lockfile
cd ..
bash scripts/dev.sh
```

dev.sh는 init --demo로 DB를 준비한 뒤 API 8000·워커 --aggregate·프론트 5173을 실행합니다. 화면은 http://127.0.0.1:5173/이며 API 문서는 http://127.0.0.1:8000/docs입니다. 종료는 Ctrl+C입니다. 데모 계정은 로그인 창의 사용자/운영자 시작 버튼으로 확인합니다.

### 프론트 환경변수

```text
# frontend/.env.local
VITE_API_BASE_URL=http://127.0.0.1:8000
VITE_NAVER_MAP_CLIENT_ID=pwt7ulakaf
VITE_NAVER_MAP_STYLE_ID=2ca6dae8-1af8-4390-b762-6f2736423d59
```

공개 Maps Client ID만 프론트에 넣습니다. 원격 API를 사용할 때는 VITE_API_BASE_URL을 브라우저에서 접근 가능한 API 주소로 바꾸고, API의 CORS_ORIGINS에 프론트 주소를 등록합니다. 환경변수 변경 후 Vite를 재시작하고 배포 파일은 다시 빌드합니다.

### 기존 서버 API를 사용할 때 프론트만 실행

```text
cd frontend
pnpm install --frozen-lockfile
pnpm dev
```

index.html을 파일로 직접 열지 않습니다. 흰 화면이면 Console의 첫 오류·터미널 오류·Network 응답을 먼저 확인합니다. 지도 키 오류는 지도 영역에 표시하도록 되어 있습니다.

### 서버에서 워커 별도 실행

```text
PYTHONPATH=backend .venv/bin/python -m app.worker --aggregate
```

API와 워커는 같은 DB·사진 저장 경로·JWT 설정을 사용해야 합니다. local 모드에서도 관리형 MySQL을 연결할 수 있으며 DATABASE_URL의 DB 이름을 kauroong으로 지정하면 됩니다.

## 8 시연과 클라우드 배포 준비

### 단일 서버 시연

```text
ENVIRONMENT=local
STORAGE_BACKEND=local
VERIFICATION_MODE=demo
DATABASE_URL=mysql+pymysql://USER:PASSWORD@DB_HOST:3306/kauroong?charset=utf8mb4
PUBLIC_API_URL=https://API_DOMAIN
CORS_ORIGINS=https://FRONTEND_DOMAIN
JWT_SECRET=서버용으로_새로_생성한_충분히_긴_비밀값
```

예제의 자리표시자를 실제 환경에 맞게 바꾸고 DB 비밀번호의 특수문자는 URL 인코딩합니다. local이라는 이름이 API를 로컬호스트에만 묶는 것은 아닙니다. 파일 저장·검증 정책과 운영 검사를 구분하는 환경 설정입니다. 외부 시연은 HTTPS와 카메라·위치 권한을 확인합니다.

### production에서 추가로 필요한 설정

| 설정 | 조건 |
| --- | --- |
| DATABASE_URL | 공유 MySQL 주소와 DB 이름 |
| JWT_SECRET | 32자 이상 별도 비밀값. API·워커·함수에 동일 적용 |
| STORAGE_BACKEND / S3_* | s3, 비공개 사진 버킷, endpoint·region·접근 키 |
| VERIFICATION_MODE / CLOVA_* | clova, API 키와 모델 설정 |
| PUBLIC_API_URL / CORS_ORIGINS | HTTPS API 주소 / 실제 프론트 origin |
| AGGREGATE_KEY | 16자 이상 집계 키. 내부 집계 요청에 사용 |
| MAP_BUCKET / MAP_JSON_KEY | 공개 지도 JSON 버킷 / 기본 map/zones.json |

현재 production 검사는 SQLite·로컬 사진 저장·demo 판별·개발용 JWT 키를 거부합니다. 교육 계정에서 접근 키 발급이 막힌 경우 단일 서버 시연은 local로 진행할 수 있지만 공유 저장소 없이 다중 API 서버로 확장하면 사진 조회와 워커 처리가 끊길 수 있습니다.

### 배포 순서

- DB 백업 → API·워커 중지 → 기존 환경변수를 유지한 채 app.cli init 1회 → API와 검증/집계 실행 경로 시작.
- 프론트에 배포 API 주소 설정 → pnpm build → frontend/dist 내용 업로드 → Global Edge 연결. Maps 허용 웹 주소와 CORS를 맞춥니다.
- HTTPS·사진 조회·큐 처리·집계를 먼저 확인한 뒤 서버 이미지와 Auto Scaling을 연결합니다. API 헬스 체크는 /health/ready를 사용합니다.

일반 app.worker는 검증만 처리합니다. --aggregate 옵션 또는 예약 집계 경로가 필요합니다. 현재 패키지의 scheduled Cloud Function은 복구·검증 후 집계도 수행하므로 중복 실행 계획을 확인해야 합니다.

## 9 검증 결과와 다음 작업

| 항목 | 확인 결과 |

위 수치는 직전 통합 시점의 검증 기록입니다. SQLite 테스트와 단위 테스트 결과를 실제 클라우드 연결 성공이나 카메라 실기기 촬영 성공으로 해석하지 않습니다.

### 다음 작업과 확인할 담당 영역

- 백엔드·DB: 관리형 MySQL에서 실제 업그레이드와 동시 요청을 검증합니다. 테스트와 운영 DB를 구분하고 백업·복원 절차를 확정합니다.
- 클라우드: Object Storage 접근 키 발급 또는 제공 가능한 권한을 확인합니다. 비공개 사진·정적 웹·공개 지도 JSON 저장소와 외부 접근 경로를 확정합니다.
- AI: CLOVA 실응답과 승인·검토·반려 기준을 사진 샘플로 확인합니다. 소나무·비수목·모호한 사진과 수종/단계 불일치를 포함합니다.
- 프론트: HTTPS에서 실제 휴대폰 카메라·GPS·권한 거부·재촬영을 확인합니다. 구 경계 근처 GPS 오차와 사용자 안내를 검토합니다.
- 배포: ALB·Private App·DB Subnet·ACG·외부 호출 경로를 연결하고 API·워커 재시작 정책을 설정합니다.
- 성능: 조회·제보·좋아요·검증 작업을 나누어 부하 테스트하고 응답 시간·오류율·DB 연결·대기 작업 수를 측정합니다. 다중 서버 테스트는 공유 사진 저장소를 갖춘 뒤 진행합니다.
- 운영 정책: 시즌 예측 자료·기본 절정일 갱신, GPS/사진 위변조 대응, 사진 보관·삭제 정책과 집계 공개 범위를 확정합니다.
